# Contributing

## New component, or extend an existing one?

Extend first. Adding a new component is the more expensive choice long
term - one more thing to document, keep accessible, keep token-only, and
keep working across three languages forever after. Before opening an issue
for a new component, check:

1. **Does an existing component already do this with a prop you haven't
   tried?** `Card` alone covers static, link, and button shapes through one
   discriminated prop union rather than three components. Read the
   component's own Storybook page - "Kapan pakai / kapan jangan" often
   answers this directly.
2. **Is this a composition of existing components, not a new primitive?**
   The `Patterns/*` screens in this Storybook are built entirely from
   existing components arranged together - most product screens are this,
   not a reason for a new component.
3. **Does the gap only show up once, in one place?** A pattern used exactly
   once in exactly one screen usually belongs in that screen's own code,
   not promoted to the design system on the strength of a single use.

If none of those hold, a new component is the right call. Open an issue
with: the use case, a mockup or clear description, and which real screen(s)
need it - the same three things `HANDOFF.md`'s "Kalau butuh komponen baru"
section asks for.

## The non-negotiable standard, every component

Every component that ships - new or extended - is held to this whether it
is Tier 1 or Tier 3 in the documentation:

- **All states.** Default, hover, focus-visible, active, disabled, loading,
  and error where the component has one - a component with a disabled prop
  and no disabled story is not done.
- **Three story sections, minimum.** A state matrix (every variant × every
  state), a dark-mode story, and a text-expansion story showing the same
  content in English, Malay and Indonesian side by side - Malay and
  Indonesian both run 15-30% longer than English for the same meaning, and
  that has to be proven to hold, not assumed.
- **Passes axe, in a real browser.** `pnpm test:a11y` runs axe-core against
  every story through an actual Chromium instance, not a DOM simulation -
  `color-contrast` specifically cannot be checked any other way (see
  `packages/ui/src/test/a11y.ts`'s own comment on why the unit-test suite
  disables that one rule). A component that only passes the unit-test
  suite's own lighter a11y check has not actually passed yet.
- **Token-only.** No literal hex, px, or duration in a component stylesheet
  - `pnpm --filter @umrahhaji/ui verify:tokens` checks every shipped
    stylesheet against the built token output and fails the build on a
    literal. `pnpm lint:ds` runs the same category of check across the
    wider repo, for the same reason.
- **44px tap targets**, even when the visible control is smaller - the
  small `NumberStepper` button and the `Carousel` dots are both drawn at
  their real visual size with an invisible `::after` overlay carrying the
  actual hit area up to 44px. Grep either component's CSS for that pattern
  before inventing a new one.
- **Generic icon → `@tailgrids/icons`, everything else → the closest fit or
  hand-drawn.** A new chevron, close button, calendar, or any other plain
  interface glyph comes from
  [@tailgrids/icons](https://tailgrids.com/docs/icons) (`import { X } from
'@tailgrids/icons'`), not a new hand-copied `<svg>` - a shared, reusable
  icon belongs in `lib/icons.tsx` the same way `CloseIcon`/`ChevronDownIcon`
  already do. It is a small (~245-icon), generic set, so check the real
  export list in `node_modules/@tailgrids/icons/dist/index.d.ts` before
  assuming a glyph exists - several call sites (the hotel amenities, a
  couple of status icons) already reach for the closest available shape
  rather than an exact match, and say so in a comment where they do.
  Domain or brand meaning that has no reasonable available shape at all -
  the prayer-room glyph, most notably - stays hand-drawn instead of forcing
  a wrong or misleading substitute, which would fail the purpose test the
  same as any other decoration with no reason behind it. `@tailgrids/icons`
  is a peer dependency (see `vite.config.ts`'s `external` comment for why it
  is never bundled into `dist/`), so a new icon import needs no package.json
  change here. One more difference from the old pack: every icon renders at
  its own fixed stroke width - there is no `strokeWidth` prop to pass.

## Adding a new token

Tokens are generated, never hand-edited. The single source of truth is
`packages/tokens/src/tokens.json`, itself generated by a Python script
(kept outside the repo in scratch space during active token work, then
regenerated on demand) rather than edited by hand - editing the generated
JSON directly gets silently overwritten the next time anyone regenerates
it.

1. Add the new primitive or semantic value to the generator script.
2. Regenerate: `python3 gen.py`, then `node scripts/build.mjs` from
   `packages/tokens`.
3. Run `pnpm --filter @umrahhaji/tokens test` - this re-checks all 174
   contrast contracts and the tabular-numeral guarantees against the newly
   built output. A new color pairing that fails contrast fails right here,
   before it ever reaches a component.
4. Rebuild `packages/ui` (`pnpm --filter @umrahhaji/ui build`) so the new
   variable actually reaches `dist/` - Storybook's dev server picks up
   source changes live, but `apps/storybook` type-checks and the built
   Storybook consume `packages/ui/dist`, which only a real build refreshes.

A token **value** adjustment (a radius, a spacing step, an elevation) is a
`minor` version bump while this design system is pre-1.0 - see
`.changeset/README.md` for the full semver table and why visual tuning
specifically does not count as a `patch`.

## Review process

Every PR runs the same CI pipeline before a human looks at it: lint,
typecheck, unit tests, `pnpm test:a11y`, contrast contracts, both packages'
build, and the bundle-size check against the committed baseline. A red CI
check is a faster, more honest first answer than waiting on a reviewer for
the same thing a script already knows.

A human review still checks the things a script cannot: whether the
"Kapan pakai / kapan jangan" table is genuinely specific rather than
generic filler, whether the component's own reason for existing (read its
top-of-file comment) still holds after the change, and whether a new prop
is the simplest shape that solves the real, stated use case rather than
the most flexible one that could theoretically solve every future one.
